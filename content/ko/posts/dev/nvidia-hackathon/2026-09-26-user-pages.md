시나리오 C로 만든 화면 1을 저녁에 직접 열어 봤다. 그리고 두 가지를 지적했다.

---

## 배경: 도구의 본질과 화면이 맞지 않았다

1. 이 도구는 사용자가 무언가를 입력하는 도구가 아니다. **통계를 스냅샷으로 받아 두고 탐지하는 도구**다. 그러니 화면은 경보 목록에서 시작해야 한다.
2. 지금 화면은 스냅샷 ID, 실행 폴더, 정책 이름, 해시가 그대로 보이는 **시스템 관리자용**이다. 내부 소스를 모르는 담당자는 쓸 수 없다.

오케스트레이터는 비공개 디자인 캔버스에 세 화면을 올렸다. 담당자 홈(월별 경보 목록), 사례 검토(평이한 설명), 보조 화면(결정 기록·재조사·도움)이다. 나는 이렇게 답했다. "해외기업에서 확인할것이니 영문 버전을 추가하고, 디자인은 이대로해줘."

## 선택지

| 안 | 판단 |
|---|---|
| 화면 1만 두고 제출(시나리오 C 그대로) | 버림 — 담당자가 쓸 수 없는 화면으로는 실용성을 보일 수 없다 |
| 보조 화면을 질의응답 채팅으로 | 제안하지 않음 — 새 모델 호출과 지침이 필요해 동결·비용 위험이 있다 |
| **담당자 화면 3개 + 영문판, 관리자 화면은 유지** | **채택** |

채점 경로는 건드리지 않았다. 결정 기록을 모의 승인 단위로 구현하면서, 아침에 범위에서 뺐던 승인 모의의 일부가 되살아났다. 화면 개수가 바뀌었으니 제출서 주장 문구도 "담당자용 3개 + 관리자용 1개"로 고쳤다. 공용 약속이라 이것도 내가 승인했다.

## v2: 필요한 것만

구현된 화면을 보고 다시 피드백을 줬다. 의미 없는 요소를 없애고, 카드·조회 조건 영역과 데이터 영역을 나누고, 열에 내부 변수명을 보이지 말고, 실행 중에는 전체 화면 로딩을 보이라는 것이었다. v2 캔버스를 본 뒤에는 열 이름, 카드 폭, 버튼 위치, 로딩 창의 "목록으로", 모든 화면의 "조사 중" 표시까지 여섯 가지를 지정했다.

담당자 화면에서 품목 코드, 스냅샷 ID, 실행 폴더, 정책 이름, 해시, 상태 코드 원문을 모두 없앴다. 예외는 "문의할 때 사례 번호" 한 줄뿐이다. 로딩 창은 대화 상자 방식 대신 고정 위치 컨테이너와 배경 하위 프로세스로 만들었다. Streamlit은 버튼마다 스크립트를 다시 돌려 동기 실행이 끊기기 때문이다.

## 검토 경로의 변경

같은 시각 Codex가 사용량 한도에 걸렸다(안내상 10월 23일까지). 운용 규칙상 Codex 판정 없이 병합하려면 내 승인이 필요했다. 오케스트레이터가 Claude 독립 검토자의 PASS로 병합하고 Codex 재검토는 한도가 풀린 뒤 받는 대체 경로를 요청했고, 나는 "PR은 병합해"로 승인했다.

## 이 선택의 의미

평가 숫자가 아무리 좋아도, 담당자가 열어서 쓸 수 없으면 실용성은 증명되지 않는다. 마지막에는 브라우저 자동화로 사용자 흐름 전체를 눌러 보는 E2E 시험을 해 16개 항목을 모두 통과시켰다(키 없이 재생 실행만). 9월 27일 새벽에는 담당자 화면에서 실자료 경보 1건으로 실제 NIM 조사를 돌려, 모델 요청 5회 모두 200, 보고서 숫자 7개 대조 일치를 확인했다.
